# Migrate admin-dashboard feature flags to PostHog

## Summary

Today all backend-driven app behaviour flows through one pipe: the admin dashboard writes JSON rows to Supabase `reference.app_config`, the server merges them (plus per-user overrides from `entitlements.admin_grants`) into `GET /api/app-config`, and the app reads them via `src/services/remoteConfig.js` with a mandatory fallback per key. "Feature flags" and "remote config" are the same mechanism today.

This ticket scopes moving the genuine *feature-flag* layer to PostHog (already integrated for analytics via `src/services/analyticsService.js`), while deliberately leaving config *values* and entitlement overrides where they are.

## What's flag-controlled today

**Group A — true on/off toggles** (`features.*`, read via `remoteConfig.getBool`, default `true`):

* `features.beginnerProgram.enabled` — 12-week beginner programme card + flow
* `features.quickPlan.enabled` — "Just get better" ongoing-plan card
* `features.stravaSync.enabled` — Strava sync globally
* `features.aiCoachChat.enabled` — Coach chat access
* `features.pushNotifications.enabled` — Push system

**Group B — gradual rollout / allowlist:**

* `strava_access.mode` (`all` | `allowlist`) + `strava_allowlist` (emails) → server derives a per-rider `stravaAllowed` boolean, read via `remoteConfig.isStravaAllowedForMe()`. Currently ~5 seeded emails.

**Group C — per-user overrides** (`entitlements.admin_grants.overrides`, deep-merged last, win over global):

* `entitlement`, `features.<x>.enabled`, `coachesUnlocked`, `trial.days`, `banner`, `forceOnboarding` — support/goodwill/beta levers from the user-detail page.

**Group D — server-driven config values** (not really flags — these are *values* edited in the dashboard):

* `maintenance_mode`, `min_version` (force-upgrade), `trial_config`, `pricing_config`, `coming_soon`, `banner`, `limits` (rate limits), plus content payloads (`copy`, `coaches`, `fitness_levels`, `plan_durations`, `workflows`).

## Recommendation

**Migrate Groups A and B to PostHog. Keep Groups C and D where they are.**

* **Group A toggles → PostHog boolean feature flags.** Direct mapping. SDK is already initialised and identifies users, so flag evaluation keys off the same distinct ID. Win: percentage rollouts + cohort targeting that the current boolean-only dashboard can't do.
* **Group B Strava rollout → PostHog cohort / % rollout.** Textbook PostHog use case. Replaces the hand-rolled email allowlist + server-derived boolean and removes the `strava_allowlist` migration/DB-edit dance.
* **Group D config values → keep in** `app_config`**.** PostHog flags are for enabling code paths, not shipping pricing/copy/store URLs/maintenance text. Moving them buys nothing and loses the typed admin form + API-compat guarantees.
* **Group C per-user overrides → keep in Supabase.** These are entitlements/support actions tied to billing (RevenueCat lifetime grants etc.), not experiments.

## Why this is more than find-and-replace

1. **Offline-first contract.** `remoteConfig` is cache-first with a guaranteed fallback so the app never blocks/crashes offline (`init()` hydrates from AsyncStorage; every getter has a default). PostHog RN SDK has local flag caching + bootstrap, but we must preserve synchronous fallback behaviour. Cleanest path: keep the `remoteConfig.getBool(...)` API surface and back Group A/B with PostHog underneath so call sites don't change.
2. **API forwards/backwards compat (hard rule, see CLAUDE.md).** Old store builds still read `features.*` and `stravaAllowed` from `/api/app-config`; we can't delete those server-side. Migration is a dual-write/ramp: server keeps emitting flags from `app_config` *and* PostHog evaluates them, until every live client reads from PostHog. Realistically the server keeps the `/api/app-config` flags indefinitely for old builds.
3. **Server-side evaluation.** `stravaAllowed` is derived server-side today. If Strava gating moves to PostHog, decide whether the server calls PostHog's server SDK to evaluate (keeps the single `stravaAllowed` boolean on the wire — best for old-client compat) or the client evaluates directly.
4. **Admin UX change.** Group A/B editing moves from `/dashboard/config` to the PostHog UI — flag this to whoever uses the dashboard.
5. **Tests.** Mocks exist for PostHog (`tests/harness/mocks/posthog.js`, `src/__tests__/mocks/posthog.js`) and remote config. Any flag whose source changes needs its test updated per repo testing rules.

## Suggested phasing

* **Phase 1** — define the 5 Group A flags + the Strava rollout flag in PostHog; bootstrap into the SDK; shadow-only (don't gate anything yet) and compare against `app_config` values to confirm parity.
* **Phase 2** — flip `remoteConfig.getBool` for Group A to read PostHog-first with the `app_config` value as fallback; keep server emitting both.
* **Phase 3** — move Strava gating to a PostHog cohort; retire the `strava_allowlist` edit path (server still emits `stravaAllowed`, now sourced from PostHog for new clients).
* Leave Groups C and D untouched.

## Key files

* `src/services/remoteConfig.js` — app-side config reader (flag consumption, fallbacks)
* `src/services/analyticsService.js` — existing PostHog integration
* `server/src/routes/appConfig.js` — `/api/app-config` (emits `features.*`, derives `stravaAllowed`)
* `server/src/routes/admin.js` — admin config write endpoints
* `admin-dashboard/src/app/dashboard/config/page.tsx` — current flag editor UI
* `supabase/migrations/*_strava_allowlist.sql` — allowlist seed
