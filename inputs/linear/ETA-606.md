# Route Planning

# ETA-604: Route Planning

## Summary

Riders need a way to find or generate a route for any ride or session — not just multi-day trips. This feature adds route planning to the core ride experience, with filtering by surface type, distance, and difficulty level, and integration with the training plan so sessions can have a route attached.

## Current State

The app already supports route planning for multi-day bikepacking trips (TripsIntroScreen, TripRouteEditor, Mapbox road snapping, AI route generation via Claude). Single-day rides and training sessions currently have no equivalent — riders cannot find or build a route for a scheduled session or a standalone day ride. The app's "Cycling Sorted" content section includes route planning guidance, but there is no in-app tool to actually plan or save a route for a session.

## Goals

* Let any rider find or generate a route for a single-day ride or training session.
* Support filtering by surface type (road, gravel, MTB), distance, and difficulty level.
* Connect routes to training plan sessions so a rider heading out for a scheduled ride knows where to go.

## Users and Needs

Beginner and returning riders who know they want to ride but don't know where. Also event trainees who want a route that matches a scheduled training session (e.g. a 2-hour endurance ride on gravel).

## User Stories, Features and Requirements

### Route search and discovery

* A rider can search for a route by describing various parameters - distance/time, start point, time, difficulty
* This shoudl generate about 3-5 different routes, which shoudl be valid routes for cyclng, and it shoudl show on the map
* When opened from within a training session, search criteria are auto-populated from the session's duration, intensity, and the rider's current or home location.
* Results are filtered and labelled by surface type, approximate distance, and difficulty level.
* Each result shows a map preview, distance, elevation, and surface breakdown.

### Strava saved routes

* For users with Strava connected, the route planning screen surfaces their saved Strava routes alongside Etapa-generated and imported routes.
* Each Strava route shows the same metadata as other routes: map preview, distance, elevation, and surface type where available.
* A rider can attach a saved Strava route to a session or save it as a standalone route in Etapa.

### AI route generation

* If no suitable discovered route exists, the rider can ask the AI to generate a route from their current location or a specified start point.
* The generated route respects the rider's chosen surface type, distance, and difficulty preferences.
* The rider can adjust waypoints and regenerate, consistent with the existing TripRouteEditor interaction model.
* Prefer open source and user-curated route data over building from scratch. Recommended options: **GraphHopper or Brouter** (both OSM-based, cycling-surface-aware, self-hostable or API) for route generation; **Ride with GPS API** or **Wikiloc** for surfacing real-world community routes. Both have free tiers suitable for early testing.

### Training plan integration

* When viewing a scheduled training session, the rider can tap to find or generate a matching route directly from the session detail.
* The session's duration and intensity inform the suggested distance and difficulty of the route.
* A saved route appears on the session card so the rider can navigate to it on the day.

### Surface types and difficulty

* Supported surface types: road, gravel, MTB/trail.
* Difficulty levels aligned with the app's existing rider level model (beginner, intermediate, advanced). Let them select difficulty

### GPX import

* A rider can upload a GPX file to attach a real-world route to a session or standalone ride.
* On import, the app extracts the route track and surface breakdown from the GPX and displays them on the session map preview.
* Uploaded GPX routes can be used as-is or adjusted in the route editor.

### GPX export

* A rider can export any saved route (AI-generated or GPX-imported) as a GPX file.
* Export uses the native OS share sheet, allowing the rider to send to Garmin, Strava, Komoot, Files, or any other installed app that accepts GPX.
* This extends the existing GPX export already available for multi-day trips to single-day sessions.

## Competitive Context

Strava and Komoot both offer route planning today. Strava's route builder is map-based and powerful but requires the user to know what they want. Komoot's route planner is strong on surface type and difficulty filtering, particularly for gravel and MTB. Neither is integrated with a training plan or coaching layer. Etapa's differentiation is the connection between route planning and the rider's actual training schedule — suggesting a route that fits today's session, not just a route in isolation. The Strava saved routes integration also reduces friction for riders who already use Strava to discover routes.

## Success Metrics

* Number of routes saved per active user per week.
* % of training sessions with a route attached.
* Route-to-ride completion rate (sessions with a route vs. sessions marked complete).

## Risks and Open Questions

* **Route data source:** AI-generated routes are coarse polylines, not GPS-grade. For discovery, we need a source of real-world routes — confirm what data source is in scope (OSM, a route API, curated set, or purely AI-generated).
* **Location permissions:** Generating a route from current location requires location access. Confirm the app's current location permission flow covers this context.
* **Training plan coupling:** Clarify how tightly routes are coupled to sessions — is a route saved per session, or can it be saved independently and linked later?

## Navigation and Information Architecture

Route planning needs to be discoverable from the bottom navigation. Currently the Goals tab covers goals, events, and trips. Adding routes to this tab raises a naming question: "Goals" may no longer be the right label for a tab that also houses trips and routes.

* **Open question:** Should the Goals tab be renamed to "Planning" (or similar) to better reflect that it encompasses goals, events, trips, and routes?
* Any rename should be considered in light of how existing users understand the tab — and whether the Cycling Sorted route planning content should also move under this tab or remain in its current location.

## Admin Observability

All route searches should be logged and visible in the admin dashboard, following the same pattern as the existing find-a-goal search tracking (`find_goal_searches` table, `GET /api/admin/find-goal-searches` endpoint, and the user detail Searches tab).

* A new `route_searches` table logs each search: user, search parameters (surface type, distance, difficulty, start point, session context), result count, data source used, and timestamp.
* A new `GET /api/admin/route-searches` endpoint exposes this data to the admin dashboard.
* Route searches appear in the user detail Searches tab alongside goal and trip searches.
* A top-level Routes page in the admin sidebar shows all searches across all users, consistent with how the Events and Find-a-Goal pages are structured.

## Feature Flags

Route planning should be gated behind a feature flag to allow controlled rollout. The app currently has a basic per-user override system via `user_config_overrides` and the admin Config page, but this does not support percentage rollouts or user-cohort targeting.

**Recommendation: PostHog (free tier).** PostHog's free tier includes up to 1M events/month and full feature flag functionality including percentage rollouts, user property targeting, and a management UI. This would be the first use of a dedicated feature flag tool in the app.

* Install the PostHog React Native SDK in the mobile app.
* Gate the route planning entry point behind a `route-planning-enabled` flag.
* Roll out initially to internal users, then a percentage of the user base, then full release.
* The existing per-user `user_config_overrides` system can remain for admin overrides; PostHog handles the broader rollout targeting.
